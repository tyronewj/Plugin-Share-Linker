# Share Linker：目标 Vault 选择器 + 目标库链接失效检测与修复

## 摘要

在现有 Share Linker 设置页上做两件事。第一，把「目标 Vault 路径」从只能手填改成能选：路径输入框保留（可手填、可粘贴、可放网络路径），旁边加「选择…」按钮打开一个 Obsidian 风格的 Modal，列出本机 Obsidian 注册表（`obsidian.json`）里记录过的库，按最近打开时间排序，标出「当前」「打开中」「目录不存在」；Modal 底部再给「浏览…」入口，走 Electron 原生文件夹对话框兜底任意新目录；注册表读不到时整个列表退化成「已保存路径 + 浏览…」，不报错。第二，新增「目标库链接健康」分区：用户点「检测链接」时扫描目标库 `.obsidian/plugins`、`themes`、`snippets` 下的符号链接与 junction，把每个链接判成健康 / 失效 / 源库不可达三态；失效项可按当前库同名资源「重建链接」，无同名源的失效项可「删除链接」，另有「全部重建」「全部删除」两个只作用于对应子集的批量按钮（各自带列出明细的确认弹窗）；删除时同步清理目标库 `community-plugins.json`、`appearance.json` 的 `enabledCssSnippets` 与 `cssTheme` 中对应条目，所有配置写入沿用现有的写前 `.bak` 备份 + 临时文件 `rename` 原子替换。

第三件事是为了回答「源库和目标库到底差在哪」：三个资源区从单列改成配对双列——左列是当前库的可勾选行（勾选 / 版本 / 描述），右列是目标库对应项的状态（已链接 / 已存在副本 / 冲突 / 链接失效 / 未共享），目标库独有、当前库没有同名项的条目以「左格留空」的行按名称顺序并排列出（链接显示指向、实体副本显示路径）；右侧状态只在点「检测链接」后填充，检测前显示「未检测」。行内原先设想的状态 chip 取消，状态由右列承担。

高保真原型：[20261101_share-linker-vault-picker-link-health-visual.html](./20261101_share-linker-vault-picker-link-health-visual.html)（Obsidian 设置页内的「选择…」已知库 Modal、链接健康分区、三态列表、批量确认弹窗、配对双列的源库↔目标库对照与全部健康态都可点）。

## 术语

| 术语 | 定义 | 避免 |
|---|---|---|
| 目标库 | 接收共享写入的另一个 Obsidian Vault；本插件始终从当前库读取、向目标库写入。 | 目标仓库、target vault |
| 失效链接 | 目标库 `.obsidian/plugins`、`themes`、`snippets` 下的一个软链接或 junction，其 `readlink` 指向的物理路径已不存在（`stat` 返回 `ENOENT`），且该路径的父目录 / 盘符仍可访问。 | 坏链接、死链 |
| 源库不可达 | 链接目标的上层目录（盘符 / 网络共享）本身访问不到，通常意味着源库所在的磁盘没挂载或网络盘断线；它与「资源被删掉」在表层症状相同，但处理方式相反。 | 目标不存在、失效 |
| 已知库 | Obsidian 自己在 `obsidian.json` 注册表里记录过的 Vault（含路径、最近打开时间、是否打开中）；本插件据此列出可选的目标库。 | 历史库、vault 列表 |
| 清理 | 删除目标库里的失效链接本身，不触碰当前库与链接曾经指向的任何内容。 | 删除插件、卸载 |
| 修正 | 把失效链接重新指向当前库中的同名资源；与清理相对，清理是删掉链接，修正是保留链接名、换掉指向。 | 修复、重新链接 |
| 启用记录 | 目标库里记录「哪些资源处于启用状态」的配置：`community-plugins.json` 的插件 ID 数组、`appearance.json` 的 `enabledCssSnippets` 与 `cssTheme`。 | 启用列表、插件清单 |
| 配对行 | 资源列表里由「当前库同名项」与「目标库对应项」组成的一行：左格是源库侧（可勾选），右格是目标库侧状态；只有一侧存在时另一格留空占位。 | 对照行、diff 行 |

## 为什么

目标 Vault 现在只能手填路径：填错要等「检查目标路径」才知道，换库要记住一长串绝对路径，网络路径与中文路径更是没法记。用户手上又往往有好几个库（本机注册表里就有 4 个），靠人脑维护路径是这次要消掉的摩擦。

第二个问题更隐蔽：插件、主题、片段以软链接共享到目标库后，链接指向的是当前库里的物理目录。当前库改名、移动、换盘符，或者源资源被删掉，目标库里的链接就静默失效——Obsidian 不会弹错误，只会表现为「目标库里的插件/主题/片段不见了」，用户要进目标库设置翻一圈才发现。更麻烦的是手动去文件管理器处理：链接和真实目录在资源管理器里长得一样，误删物理资源的风险实打实存在。所以除了「检测出引用的物理路径不存在就提醒」，还要把处理动作做进插件里：能修的直接重指，修不了的（源已删）安全删除链接，并顺手把目标库启用记录里的幽灵条目清掉。

第三件事是「差异在哪看」。共享前用户只能看到当前库有什么，看不出目标库那边已经有什么、缺什么、坏没坏；动作之后也只有一张会被下次操作清空的共享结果卡片。双向差异是这次评审中补上的要求：既要看到「当前库这一项在目标库是什么状态」，也要看到「只在目标库有、当前库没有」的条目。它被做成了资源列表的配对双列（见 D5），而不是另一个独立的对照页面。

## 已定决策

### D1 选择器：已知库列表为主，「浏览…」原生对话框兜底（q1 = C）
- **决策：** 路径输入框保留，旁边加「选择…」按钮：Modal 列出 `obsidian.json` 注册表里的库（排序列见 q4），Modal 底部放「浏览…」，用 Electron 原生文件夹对话框选任意目录（包括还没被 Obsidian 打开过、因而不在注册表里的新目录）。两条路径任一不可用时另一条必须仍然可用。
- **理由：** 唯一同时覆盖「注册表里的老库」和「从未打开过的新目录」的方案。注册表列表能显示「打开中」（提醒用户先关目标库再共享，现有提示依赖它），原生对话框能选到任何盘上的新文件夹——单独任何一条都会漏场景。
- **实测依据：** 本机 `C:\Users\Administrator\AppData\Roaming\obsidian\obsidian.json` 形如 `{"vaults":{"<hash>":{"path":"E:\\知识库_公司","ts":1793468021320,"open":true},…}}`；同目录的 `obsidian-1.14.5.asar` 内部自己就在调 `electron.remote.dialog.showOpenDialogSync`，并在 `electron.remote` 缺失时回退 `require("@electron/remote")`，说明桌面端 `require("electron").remote` 可用，但仍要 try/catch。

| 选项 | 用户体验 | 技术正确性 | 风险 | 成本 |
|---|---|---|---|---|
| A 只加原生对话框 | good | good | mixed | good |
| B 只做已知库列表 | good | mixed | good | good |
| C 两者都做（**决策**） | good | good | good | mixed |
| D 只给输入框加路径补全 | poor | poor | good | good |

- **被否决：** A 单独用把可用性押在一个非公开 API 上（`remote` 未来可能被移除）；B 选不到注册表里没有的目录，而「给一个还没成为库的新文件夹建 `.obsidian`」正是现有 resolveTargetVault 明确支持的场景；D 的补全只能覆盖当前库内路径，跨库无用。
- **一致性说明：** 决策 C 的最弱轴是 cost（mixed）：要维护两条选择路径（Modal + 原生对话框）和一条降级分支，代码量与文案都比单选一种多。这条成本换来的是两条路径互为兜底，收益体现在 risk 而不是 ux 上——用户平时只会用其中一条。

### D2 失效链接的主处理是「重建」，无同名源时才允许「删除」（q3 = 仅 B，q6 = A）

- **决策：** 检测结果里，失效链接默认提供的是「重建链接」——在当前库已校验的三份列表（插件 / 主题 / 片段）里按文件夹名 / 文件名找同名项，把链接重指过去（q10）。只有「当前库没有同名资源」的失效项才显示「删除链接」，并且批量「全部删除」只作用于这一子集（q8）。用户最初提的是「清理或修正」，这里把「修正」放主位、「清理」放在无源兜底，是为了让默认动作尽量是保留链接名的修复，而不是删除。
- **理由：** 大多数断链来自源库搬家或改名，资源本身还在，重建即可恢复且不损失任何东西；删除只应在修不了时发生。

| 选项（q3） | 用户体验 | 技术正确性 | 风险 | 成本 |
|---|---|---|---|---|
| A 删除失效链接 | good | good | mixed | good |
| B 重建链接到当前库同名项（**决策项之一**） | good | mixed | good | good |
| C 改为复制当前库同名资源 | mixed | good | mixed | mixed |
| D 逐条手动指定新目标路径 | poor | good | mixed | mixed |

| 选项（q6，无同名源时） | 用户体验 | 技术正确性 | 风险 | 成本 |
|---|---|---|---|---|
| A 提供「删除链接」兜底（**决策**） | good | good | mixed | good |
| B 只标记「无法自动修正」不动 | poor | good | good | good |
| C 提供「改为复制」但不能删除 | mixed | mixed | mixed | mixed |
| D 提供「手动指定新目标路径」 | poor | good | mixed | mixed |

- **被否决：** q3 的 C 会造出不再与当前库同步的独立副本；q3 的 D 把一行一个绝对路径输入塞回设置页。q6 的 B 把清理推回文件管理器（正是这次要消掉的摩擦）；q6 的 C 在源资源不存在时本就不可复制，能复制时也没解决旧链接；q6 的 D 让一个可一键完成的动作变成手写路径。
- **一致性说明：** 决策 B 的最弱轴是 correct（mixed，q3 表里）：只按名字匹配，同名不同源会指错，所以重建结果必须显式写出「原指向 → 新指向」供核对（q10 的 A 同时决定不做 manifest id 兜底，避免造出文件夹名与 `manifest.id` 不一致的链接——Obsidian 按文件夹名识别插件）。q6 的 A 最弱轴是 risk（mixed）：删除链接不可撤销，且目标库可能仍启用着它，所以删除必须二次确认（批量时列明细）并同步清理启用记录（D3），备份文件保证配置可回滚。

### D3 删除失效链接时，同步清理目标库启用记录（q7 = A）

- **决策：** 删除失效插件链接 → 从目标库 `community-plugins.json` 移除该插件 ID；删除失效片段链接 → 从 `appearance.json` 的 `enabledCssSnippets` 移除该片段名；删除失效主题链接 → 若 `cssTheme` 等于该主题名，清空该字段（q13）。只删「本次删掉的链接」对应的那些条目，其他条目一律不动；写入沿用写前 `.bak` 备份 + 临时文件 `rename` 原子替换；`appearance.json` 的片段与主题两处改动合并为一次读-改-写，避免互相覆盖（沿用既有 q6 约束）。
- **理由：** 不清理的话，目标库配置里会长期留着一个已经不存在的插件 ID / 片段名 / 主题名。Obsidian 对缺失项基本静默忽略（不会崩溃），但配置与现实不符，用户下次在目标库设置里排查时会被幽灵条目误导；主题的 `cssTheme` 更直接——主题文件已经没了，Obsidian 已经在回落默认主题，配置却还写着旧名字。
- **与既有 D1（共享时只追加、不接管启用列表）的关系：** 那条决策保护的是「不要替用户关掉目标库自己开着的插件」。这里删的是用户刚刚确认要清理的失效项对应的条目，语义是「让配置追上刚发生的事实」，不是接管偏好；备份文件是两者共同的兜底。

| 选项 | 用户体验 | 技术正确性 | 风险 | 成本 |
|---|---|---|---|---|
| A 同步清理（**决策**） | good | good | mixed | mixed |
| B 只提示、不改配置 | poor | good | good | good |
| C 确认框里给默认勾选的「同时清理」选项 | mixed | good | mixed | mixed |
| D 只把幽灵条目标出来让用户处理 | mixed | mixed | good | mixed |

- **被否决：** B 让清理做一半；C 把「删链接」和「改配置」两个意图混在一次确认里，选择成本高且容易误选；D 不解决链接本身，只是把幽灵条目挪到另一个列表。
- **一致性说明：** 决策 A 的最弱轴是 cost（mixed）与 risk（mixed）：这是插件第一次「删」目标库配置文件里的内容，要新写三条删除逻辑与一次合并写，并依赖既有备份机制兜底。q13 = A 的理由同理：主题文件已失效时 `cssTheme` 指向的名字没有任何可用对象，清空只是让配置追上现实。

### D4 断盘与单链接失效必须区分：源库不可达项禁止删除与重建（q14 = A）

- **决策：** 检测结果三态：健康 / 失效 / 源库不可达。判定：`stat(链接自身)` 成功 → 健康；失败时看链接目标的盘符或网络共享根（以及最近可访问的祖先目录）是否还能访问——能访问但目标不在 → 失效；上层就访问不到 → 源库不可达。源库不可达行只显示状态与「先挂载源库再检测」提示，重建与删除按钮禁用，也不进入任一批量操作。
- **理由：** 源库所在的移动硬盘拔掉或网络盘断线时，所有链接的 `stat` 都返回 `ENOENT`，与「资源被删」完全同形。此时若按失效处理，「全部删除」会一键清掉一整套本来完好的链接。
- **实测依据：** Node v24 下，Windows 目录软链接与 junction 在目标消失后都是 `lstat().isSymbolicLink() === true`、`readlink()` 返回原目标、`stat()` 抛 `ENOENT`；`fs.rm(path, { force: true })` 只删链接本身（对两种链接都成立），不触碰目标。因此「先 lstat 认链接、再 stat 认存在」是可靠判定链。

| 选项 | 用户体验 | 技术正确性 | 风险 | 成本 |
|---|---|---|---|---|
| A 三态并禁用危险动作（**决策**） | good | good | good | mixed |
| B 两态，靠显示原路径让用户判断 | good | poor | poor | good |
| C 两态，批量删除确认里额外警告 | mixed | mixed | mixed | mixed |

- **被否决：** B 把安全判断完全交给用户看路径；C 的一句警告挡不住已经习惯批量操作的手，而三态本身还能给出正确指引（治断盘要插回硬盘，不是清理）。
- **一致性说明：** 决策 A 的最弱轴是 cost（mixed）：每个失效链接要多做一到三次祖先目录 / 根探测的 `stat`，列表多一种状态与文案。这个探测只在链接已经 stat 失败时才发生，健康链接是零额外成本。

### D5 双向差异用配对双列，在检测时一次算出（q15 = B「要体现双向差异」，q16 = 「折叠改为双列并排」，q17 = A）

- **决策：** 插件 / 主题 / CSS 片段三个分区各改成配对双列：左列是当前库的可勾选富行（共享 / 启用勾选、名称、版本、描述），右列是目标库对应项的状态——已链接 / 已存在副本 / 冲突 / 链接失效 / 未共享；冲突与失效在右列显示指向路径；检测前右列一律显示「未检测」。当前库没有同名项、但目标库里有的条目，作为「左格留空（当前库无同名项）」的行按名称顺序并入同一列表并排列出，只读、不可勾选、不提供动作。行内状态 chip 取消（右列承担同一件事），页面顶部只保留一份五态 + 未检测的图例。
- **配对规则：** 按名称（插件 / 主题的文件夹名、片段的文件名）在当前库三份已校验列表和目标库三目录条目之间配对；插件区的分页作用于合并后的行集（源库行 + 目标库独有行）。
- **数据来源：** 全部在「检测链接」的同一次扫描里算出——三个目标库目录本来就要 `readdir`，对每个条目再 `lstat` 判链接 / 实体；不新增目标库访问，不自动检测（Q2）。
- **理由：** 差异真正被用到的时刻，就是用户在资源列表里勾选共享的那一刻，所以状态贴在行上、按名称配对并排，能一眼看出「这项在目标库已存在 / 冲突 / 失效」和「这项只在目标库有」；同一个扫描结果同时喂给右列与「链接健康」分区，没有第二套访问路径。

|---|---|---|---|---|

| B 行内目标库状态 chip（**决策的起点**） | good | mixed | good | mixed |

| C 三列表格（资源 / 当前 Vault / 目标库） | good | good | good | poor |
| D 维持单列 + 行内 chip + 底部并排小卡 | mixed | good | good | mixed |

- **被否决：** q15 的 C（独立对照视图要再维护一张四组表格与一套勾选交互，与健康分区职责重叠）、D（差异推回动作之后，答不了「我现在该不该勾这一项」）、A（就是评审提出的问题本身）；q16 的 A（把另一半差异放到离决策更远的健康分区）、C（Modal 入口藏一层）、D（只报数字不给看）；q17 的 B（两列各自完整，同名项位置不同，眼睛要在两个列表里找）、C（勾选 / 版本 / 描述挤进窄格）、D（回到折叠变体，没有并排）。
- **一致性说明：** 决策 A 的最弱轴是 cost（poor）：三个分区的渲染器要重写成「合并行集 + 左右两格」，插件区的分页、全选（只选源库行）与「已存在 / 冲突」的既有文案都要跟着调，是这次改动量最大的一块。risk 是 mixed：按名称配对在「同名不同源」时会配错行，所以右列必须显示指向路径兜底；双列在 Obsidian 设置页约 700px 的内容宽度下每列偏窄，长描述需要验证换行。

## 常规选择

- **q2 检测时机：** 新增独立的「检测链接」按钮，只在用户点击时访问目标库。不做「打开设置页自动检测」（目标库失联时会让设置页卡住，目标库可能是网络盘 / 云盘占位 / 已拔掉的移动硬盘），也不把检测塞进现有「检查目标路径」按钮（会让路径检查与链接扫描的错误原因混在一起），不在共享动作结束后自动检测（写完后刚落地的项不可能失效，信息价值低）。
- **q4 已知库列表来源：** 只读 `obsidian.json` 注册表，按 `ts`（最近打开时间）倒序；设置里已保存的路径即使不在注册表里也置顶显示并标「当前」；每条都先 `stat` 过滤——目录不存在的保留但灰显并标「目录不存在」（让用户知道注册表里有它、但盘不在了），当前 Vault 本身标「当前库，不可选」。不做「扫当前库同级目录」（会把无关文件夹摊在眼前，且从未打开过的新目录由「浏览…」覆盖），不做插件自维护的历史目标（上次用了哪个，设置里本来就存着）。
- **q5 结果落点：** 在目标路径区域之后、插件分区之前新增独立分区「目标库链接健康」。不复用「共享结果」卡片（那张卡片每次共享都会被清空，不适合放需要逐条操作的健康列表），不把计数分散到三个资源分区，也不做成需要先有结果的 Modal。
- **q8 批量操作：** 每行单独操作 + 分区顶部两个固定批量按钮：「全部重建」只作用于有同名源、当前库校验通过的失效项；「全部删除」只作用于无同名源的失效项；两者各自弹确认 Modal，逐条列出名称与原指向（重建还列新指向），确认后逐条执行并汇总 Notice。不做行级勾选 + 批量工具条（多一层选择状态与全选/反选心智，而实际失效项要么全无源、要么全可重建），也不只做逐行操作（源库整体搬家时会退化成逐条点十几次）。
- **q9 检测范围：** 只报「物理路径不存在」，即 `stat(链接)` 返回 `ENOENT`。不报「存在但缺关键文件」（插件缺 `manifest.json`、主题缺 `theme.css`、片段指向非 `.css`），也不报「指向别的库」——重建之后指向的一定是当前库三份已校验列表里的资源，这类「存在但不可用」的情况不会经由本功能的动作产生；跨库指向本身也不等于坏。
- **q10 同名判定：** 只按文件夹名 / 文件名在当前库三份已校验列表里匹配（插件 `folderName`、主题 `folderName`、片段 `fileName`），命中即可重建，未命中即无源。不做 manifest id 兜底（Obsidian 按文件夹名识别插件，造出 `folderName` 与 `manifest.id` 不一致的链接可能加载失败或显示错乱），不做逐行候选下拉，不做手填路径重建。
- **q11 选择器形态：** 保留路径输入框（可手填 / 粘贴 / 放网络路径），右侧加「选择…」按钮，Modal 内列已知库（按 q4 规则），Modal 底部放「浏览…」原生对话框入口。不把输入框换成下拉框（注册表读不到就整条选择链断掉，也丢掉了手填能力），不做 `datalist` 补全（跨库场景难发现，展示不了「打开中 / 已失效」这类决定性信息）。
- **q12 提醒形式：** 分区标题旁显示「N 个失效」徽标 + 常驻列表；每次检测结束弹一条 Notice 汇总（含 0 个失效时的「未发现失效链接」）。不做「只列表不弹 Notice」（少了即时反馈，与现有复制 / 软链接完成弹 Notice 的习惯不一致），不做「目标路径下方常驻警告条」（检测失败与发现失效会混在同一条横幅上）。
- **q13 主题的 `cssTheme`：** 删除失效主题链接时，若 `cssTheme` 等于被删主题名则清空该字段（回归默认主题），结果里写明，配置写前备份。不做「只提示不动」（留下永远指向不存在主题的字段，下次共享同名主题时还会被误认为「目标库当前主题」），不做「仅当被删主题是当前主题时弹窗询问」（把一条批量操作拆成 N 次确认）。

## 验证过的事实

- **本机 Obsidian 注册表（Windows）：** `C:\Users\Administrator\AppData\Roaming\obsidian\obsidian.json` 存在，结构为 `{"vaults":{"<hash>":{"path":"…","ts":<毫秒时间戳>[,"open":true]}},"language":"en"}`；本机有 4 条记录，其中 `E:\知识库_公司` 带 `open:true`。同目录 `obsidian-1.14.5.asar` 说明本机 Obsidian 版本为 1.14.5。
- **Electron 原生对话框可用性：** `obsidian-1.14.5.asar` 内部代码 `var e=electron.remote.dialog.showOpenDialogSync({…})` 与 `if(!i.remote)try{i.remote=n("@electron/remote")}` 说明 Obsidian 桌面端主窗口有 `electron.remote`，并在缺失时回退 `@electron/remote`。社区插件因此可以 `require("electron").remote.dialog.showOpenDialog({ properties: ["openDirectory"] })`；仍要包 try/catch 并在失败时退回已知库列表 / 手填。
- **链接的 Node 行为（Windows，Node v24.18.0，实测）：** 目录软链接与 junction 在目标删除后：`lstat().isSymbolicLink()` 均为 `true`、`isDirectory()` 均为 `false`；`readlink()` 返回创建时写入的目标（实测为绝对路径）；`stat()` 抛 `ENOENT`。`fs.rmSync(link, { force: true })` 能删除这两种链接且不触碰目标（删除后目录为空）。
- **测试环境约束：** `tests/obsidian-stub.js` 只桩了 `Plugin` / `PluginSettingTab` / `Setting` / `ButtonComponent` / `Notice`，没有 `Modal`；`Module._resolveFilename` 只重定向 `obsidian`，没有 `electron`。因此 `require("electron")` 必须延迟到函数内部并包 try/catch（测试环境会 `MODULE_NOT_FOUND`，应走降级路径）；Modal 相关内容要么给 stub 补 `Modal`，要么把「可选库行」构造成纯函数单独测试、Modal 渲染只做薄封装。
- **现有可复用设施：** `runWithTimeout`（`TARGET_ACCESS_TIMEOUT_MS=15000`、`SYMLINK_TIMEOUT_MS=20000`、`ACTION_TIMEOUT_MS=300000`）、`readJsonFile` / `backupFile`（写前 `.bak`）/ `writeJsonFile`（临时文件 + `rename` 原子替换）、`readDirSafe` / `isFile`、`shareEntry` 的「已存在 / 冲突 / 创建」三分支、`createSection`（页内分区）、`setToolbarButtonLabel`（按钮图标 + 文本）、`TEXT` 双语字典、`logDebug` / 调试轨迹。现有共享流程在 `resolveTargetVault` 里对目标库固定用 `.obsidian`（`CONFIG_DIR_NAME`），健康检测沿用同一约定。

## 实施要点

### 新增的插件侧方法（`PluginShareLinker`）

- `listKnownVaults()`：定位 `obsidian.json`（优先 `require("electron").app.getPath("userData")`，失败按平台回退：Windows `%APPDATA%\obsidian\obsidian.json`、macOS `~/Library/Application Support/obsidian/obsidian.json`、Linux `~/.config/obsidian/obsidian.json`），读取并按 `ts` 倒序；对每条 `fs.stat` 过滤，标注 `exists`、`open`、`isCurrent`、`isSaved`；返回 `{ ok, vaults, error }`，读失败时 `ok:false` 并带原因。
- `scanTargetVault(targetVaultPath)`：先 `resolveTargetVault`（校验目标路径存在、是文件夹、不是当前库），再扫 `.obsidian/plugins`、`themes`、`snippets`；对每个条目 `lstat`，链接项 `readlink` + `path.resolve(path.dirname(entryPath), raw)` 得绝对目标，`stat(entryPath)` 成功记 `healthy`，失败则按 D4 判定 `broken` / `unreachable`；非链接项记 `copy`（供双向差异配对用）。每类目录缺失视为空组。整体套 `runWithTimeout(…, 45000, t("actionTimeout", 45))`，超时 / 目标库失联时抛出并保留上一次结果。返回 `{ target, kinds: { plugins, themes, snippets }, summary, scannedAt, elapsedMs }`。
- 双向差异不额外访问目标库：`scanTargetVault` 的结果已经包含目标库三目录里的全部条目（链接与实体副本），设置页用纯函数 `mergeDiffRows(kind, sourceRows, targetEntries)` 把当前库三份已校验列表与目标库条目按名称合并、排序，插件区分页作用于合并行集；每行右列状态由纯函数 `describeTargetRow(row)` 给出（linked / copy / conflict / broken / unreachable / unshared）。
- `findSameNameSource(item)`：在 `listPlugins()` / `listThemes()` / `listSnippets()` 结果里按 `folderName` / `fileName` 匹配，返回源路径或 `null`。
- `rebuildTargetLink(item, source)`：重新 `lstat` 确认仍是链接，并 `stat` 确认目标仍不可用（链接若已恢复有效则抛错跳过）；`readlink` 保存旧目标；`fs.rm(entryPath, { force: true })` 删旧链接；`fs.symlink(source.sourcePath, entryPath, item.kind === "snippets" ? "file" : "dir")` 建新链接（套 `SYMLINK_TIMEOUT_MS`）；失败则用旧目标尝试恢复链接，恢复也失败时返回 `error` 并给出两条路径。返回 `{ status, oldTarget, newTarget }`。
- `deleteTargetLink(item)`：重新 `lstat` 确认仍是链接、`stat` 确认目标仍不可用（已恢复有效的链接拒绝删除）；`fs.rm(entryPath, { force: true })`；收集被删项后调用 `cleanTargetEnabledRecords(target, removed)`（片段名按去 `.css` 的基础名清理）。
- `cleanTargetEnabledRecords(target, removed)`：一次读-改-写合并处理 `community-plugins.json`（过滤 `removed.pluginIds`）、`appearance.json`（过滤 `enabledCssSnippets` 中的 `removed.snippetNames`；`cssTheme` 命中 `removed.themeNames` 时删除该字段）；文件不存在跳过；解析失败沿用 `configParseWarning` 的语义（备份后按空内容处理）并记 warning；无改动时完全不写文件。返回 `{ pluginsRemoved, snippetsRemoved, themeCleared, backups, warnings }`。
- 批量入口在设置页：`confirmBulkRebuild(entries)` / `confirmBulkDelete(entries)` 先弹 `TargetActionConfirmModal` 列出明细，确认后由 `runBulkRebuild(entries)` / `runBulkDelete(entries)` 逐条调用上面的单条方法，汇总成功 / 失败并弹 Notice；成功重建 / 删除的条目同步更新页面态 inventory 与汇总计数（`markEntryHealthy` / `removeInventoryEntry`）。

### 设置页（`PluginShareLinkerSettingTab`）

- 目标 Vault 行：现有 `Setting.addText` 保留（`onChange` 继续即时保存），在其后加两个 `ButtonComponent`：「选择…」（打开 `TargetVaultPickerModal`）、「浏览…」（`browseTargetVault()`）。「浏览…」不可用时禁用并给 tooltip 说明。
- `TargetVaultPickerModal extends Modal`：标题「选择目标 Vault」，副标题「来自 Obsidian 已记录的库」；列表行复用设置页行样式（新增 `.plugin-share-linker-vault-row`）；行内：路径（`<code>`）、`当前` / `打开中` / `目录不存在` chip；不可选行禁用。底部：`浏览…`、`取消`。选择后写 `settings.targetVaultPath`、`saveSettings()`、Notice、关闭 Modal 并 `display()` 刷新。
- `buildLinkHealthSection(containerEl)`：在目标路径区域后、`buildPluginsSection` 前调用；标题行 = `h3` + 徽标 span（无异常时隐藏）+ 「检测链接」按钮 + 引导文案；结果容器按 plugins / themes / snippets 三组渲染，只列异常行；每行 = 名称 + 状态 chip + `指向 <code>` + 操作按钮（重建 / 删除；不可达行按钮 `setDisabled(true)` + 提示）；顶部批量栏只在有可操作项时出现。
- 三个资源分区改用配对双列渲染（D5）：左格复用现有行结构（勾选 / 名称 / 版本 / 描述），右格按目标库状态渲染；只在目标库的行左格显示「当前库无同名项」占位、无勾选与操作，右格显示目标条目本身（类型「链接 / 实体副本」+ 指向或路径）；检测前右格统一「未检测」；状态 chip 与五态图例在分区顶部只出现一次；插件区的分页、全选只作用于源库行；行内 chip 的代码路径删除。
- `TargetVaultPickerModal` 与确认弹窗需要新增 `Modal` 类；`tests/obsidian-stub.js` 补一个最小 `Modal`（构造 `{ contentEl, titleEl }`，`open`/`close` 空实现）以让 UI 测试可渲染分区。
- 新增 `TEXT` 文案（中英各一份，约 25 条）：选择器标题 / 副标题 / chip（当前、打开中、目录不存在、当前库不可选）/ 浏览提示 / 注册表读取失败提示 / 检测按钮与提示 / 三态 chip / 批量按钮 / 确认弹窗标题与明细 / 删除与重建结果文案 / 全部健康文案 / 超时与失败文案。
- 每条操作完成后不自动重新检测，只更新被操作的那一行（行变「已修正」或移除），徽标同步减计数；用户可再点「检测链接」全量复扫。

### 状态与持久化

- 不新增持久化设置：选择器不需要新 key（路径仍存 `targetVaultPath`），健康检测结果是页面态（`this.linkHealth = { groups, summary, scannedAt }`），每次打开设置页重新开始（Q2 = 手动检测）。

## 风险

1. **`electron.remote` 是非公开 API。** 实测 Obsidian 1.14.5 自己就在用并在缺失时回退 `@electron/remote`，但未来 Electron 版本可能整体移除 remote。降级路径是已知库列表 + 手填，功能不会消失，只是少一个「浏览…」。
2. **注册表路径 / 格式跨平台未逐一实测。** Windows 已实测；macOS / Linux 按 Electron `userData` 约定推断（`~/Library/Application Support/obsidian`、`~/.config/obsidian`），若安装方式不同读不到，则走读失败降级。
3. **Windows 建链接权限。** 重建沿用在 1.0.4 已使用的 `fs.symlink(source, target, "dir" / "file")`；没有开发者模式或管理员权限时会失败，沿用现有结果文案。未加 junction 回退（列入后续）。
4. **三态判定是启发式。** 网络共享的中间路径缺失、权限错误（`EACCES`）、链接环（`ELOOP`）都可能被判成「不可达」而暂时不可操作——这是刻意的保守方向：宁可少删，也不能在断盘时批量删链接。
5. **修改目标库启用记录是首次「删」配置。** 备份 + 原子写 + 只删本次链接对应的条目；JSON 解析失败时沿用「备份后按空内容处理」的既有行为，可能丢用户原文件内容，但 `.bak` 可回滚。
6. **重建是「先删后建」两步，非原子。** 建链接失败时会尝试恢复旧链接；极端情况下（恢复也失败）目标库会暂时少一个链接，结果里给出明确路径，用户可再检测一次修复（此时该链接已不存在，需要手动重建或重新共享）。
7. **目标库 Obsidian 正在运行时写配置可能被覆盖。** 既有风险，沿用「目标库里的 Obsidian 请先关闭」的固定提示。
8. **检测是手动的。** 用户不点就不知道已经断链；后续可考虑「打开设置页时展示上次结果摘要」，本次不做。
9. **已知库列表可能过长 / 陈旧。** 注册表里的库不会过期清理，列表按最近打开排序且灰显不存在的库；数量通常个位数，可接受。
10. **配对双列在窄容器里偏挤。** Obsidian 设置页内容宽度约 700px 量级，两列分下来每列只有三百多像素：长描述、长文件名、`<code>` 路径都要验证换行与截断；插件分页的行数与每页条数（5 起）也要在双列下重新看一遍空格感。
11. **配对按名在「同名不同源」时会配错行。** 例：当前库与目标库各有一个叫 `dataview` 但来源不同的目录，右列状态会显示到错误的左行上；兜底是右列显示指向路径，并在后续可考虑按 `manifest.id` 做二次校验（本次不做）。
12. **「只在目标库」的条目只展示、不处理。** 用户能看到目标库独有的链接或副本，但本次不提供删除 / 清理动作；若这些条目本身该清理，需要另开一轮需求。

## 验收清单

1. 目标 Vault 行：输入框可编辑且即时保存；「选择…」打开 Modal，列出注册表里的库并按最近打开排序，标「当前」「打开中」「目录不存在」（不可选）；选中回填并保存、弹 Notice；注册表读不到时 Modal 退化为「已保存路径 + 浏览…」且不报错；桌面端「浏览…」能打开系统选目录窗口并回填。
2. 「目标库链接健康」分区位于目标路径区域与插件分区之间；未检测时显示引导文案；「检测链接」手动触发，检测中按钮禁用并有进行中文案。
3. 三态正确：源目录还在、目标缺失 → 失效；盘符 / 根不可访问 → 源库不可达（重建与删除禁用，提示挂载源库）；健康只计数不列行；三类目录缺失时显示该类 0 项而不报错。
4. 失效且当前库有同名项 → 「重建链接」成功，行显示「原指向 → 新指向」，插件 / 主题为目录链接、片段为文件链接；重建失败时提示错误并尽量恢复旧链接。
5. 失效且当前库无同名项 → 只有「删除链接」；批量「全部重建」只选有源项，「全部删除」只选无源项，各自弹确认并列出明细；不可达项不进入任何批量操作。
6. 删除后：链接消失，目标库 `community-plugins.json` / `appearance.json`（`enabledCssSnippets`、命中时的 `cssTheme`）对应项被移除，`.bak` 备份存在，其他条目与字段不变。
7. 目标库失联 / 超时：检测在超时时间内报错并以 Notice + 分区提示结束，设置页不卡死，上一次结果不被清空。
8. 现有能力无回归：复制 / 软链接 / 启用写入 / 主题单选 / 语言切换 / 分页 / 调试轨迹行为不变；`node tests/run.js` 全绿。
9. 中英文案齐全，新增 UI 在两种语言下无溢出或截断。
10. 双向差异：点「检测链接」后，三个资源区每个源库行右格显示目标库状态（已链接 / 已存在副本 / 冲突 / 链接失效 / 未共享），冲突与失效显示指向路径；检测前右格全是「未检测」。
11. 「只在目标库」的条目按名称顺序出现在同一列表里：左格显示「当前库无同名项」占位、不可勾选、无操作，右格显示类型（链接 / 实体副本）与指向或路径；插件区分页与全选只作用于源库行。
12. 配对双列在 Obsidian 设置页宽度下不溢出：长描述、长路径按既有样式换行或省略，五态图例在两种语言下都完整。
13. 守卫：对已恢复有效的链接调用重建或删除会被拒绝（「这个链接现在指向有效目标，已跳过」），不会误伤健康链接；检测过程中切换目标库时，旧目标库的扫描结果会被丢弃。
