# Share Linker：目标库检测（设置检测并入「目标库检测」分区）

## 摘要

设置页里的「目标库链接健康」改名为**「目标库检测」**，并成为目标库状态**唯一的手动检测入口**：一次「检测」同时扫描目标库 `plugins / themes / snippets` 下的链接与 `.obsidian/` 根下的 8 份设置文件，给出链接健康与设置文件差异两份结果。检测**只在按钮里跑**（打开页面、换目标路径、共享完成都不自动检测）；检测分区**只显示汇总**（徽标只数链接问题，另有一行链接汇总与一行设置文件汇总），逐项状态与处理动作回到它所属的分区——插件 / 主题 / CSS 片段的行内显示目标状态并带「重建链接 / 删除链接」，各分区工具栏带「全部重建 / 全部删除」，设置的行内显示状态 chip 与悬停差异详情并带「共享此项」；失败时保留上一次结果并标时间戳，链接段与设置段各自超时、各自报错；共享完成后按影响面失效（设置共享只清设置结果，资源共享只清链接结果），不再自动重跑。用户可见文案与代码标识符整体改名（`health*` → `targetCheck*`），历史 markdown 设计文档不回改。设置共享本身的语义（键级合并、`.bak` + 原子替换、确认弹窗列键名）不变。

高保真原型：[20261104_share-linker-target-vault-detection-visual.html](./20261104_share-linker-target-vault-detection-visual.html)（Obsidian 设置页内改名后的「目标库检测」汇总区、各分区行内状态与动作、设置行 chip / 悬停 / 「共享此项」，以及未检测 / 已检测 / 检测失败 / 部分失败四种状态都可切换）。

本文取代 [20261104_share-linker-vault-settings-design.md](./20261104_share-linker-vault-settings-design.md) 里与检测有关的描述（该文档的摘要、q7 的实时自动检测、已验证事实里的「设置区按用户要求改成实时自动检测」）。按 D6，旧文档本身不回改，只在本文记录差异。

## 术语

| 术语 | 定义 | 避免 |
|---|---|---|
| 目标库检测 | 设置页里统一检测目标库状态的分区：一次检测同时给出链接健康与设置文件差异，是目标库状态唯一的检测入口。 | 目标库链接健康、链接健康分区、检测设置 |
| 检测 | 点「目标库检测」里的「检测」按钮后执行的一次扫描：读目标库的链接与设置文件，产出链接状态与设置文件状态。 | 检测链接、检测设置、实时检测、自动检测 |
| 设置文件状态 | 每份设置文件在目标库里的情形：相同 / 有差异（N 个键）/ 缺失 / 源库无此文件。 | 设置差异检测、比较结果 |
| 链接状态 | 目标库 `plugins / themes / snippets` 下的每个链接或副本的状态，沿用配对行右列的词：已链接 / 已存在副本 / 冲突 / 链接失效 / 源库不可达 / 未共享 / 未检测。 | 健康度、链接健康分 |
| 上次检测 | 最近一次成功完成的检测里，各段结果产生的时间（链接段与设置段分别记录），用于失败时标「以下为 14:32 的结果」。 | 缓存时间、快照 |

## 为什么

现在的检测是两套：设置分区在页面渲染时就在后台自动访问目标库、比较 8 份设置文件（`main.js:2003` → `refreshSettingsStatuses`，`main.js:1637`），而「目标库链接健康」分区只有点「检测链接」才扫链接（`main.js:2432`）。同一个目标库被两套节奏、两个超时、两处错误状态分开管：网络盘断开时，设置页一打开就要等一次目标库 IO；链接的结果和设置的结果没有任何共同的时间基准；两处各自把「失效 / 差异」放在自己的分区里，用户要看「目标库到底怎么样」得在两个分区之间拼。

同时，检测结果与处理动作也被放错了地方：链接失效项集中在健康分区里带「重建 / 删除」，设置差异留在设置分区里才有共享按钮，用户在哪个分区看到问题，就要去另一个分区处理。

这次要的是：一个「目标库检测」入口、一份带时间的结果、一处汇总；逐项状态与动作回到资源自己的分区，在哪儿看到问题就在哪儿处理。设置共享本身的写入语义、确认流程、备份策略全部不动（见[设置设计文档](./20261104_share-linker-vault-settings-design.md)）。

## 已定决策

### D1 检测全手动：只在「目标库检测」的按钮里跑（q1 → A）

- **决策：** 打开设置页、换目标路径、共享完成都不自动检测；「目标库检测」里的「检测」按钮是唯一入口，点一次同时扫描链接与设置文件。首次检测前，所有分区里的状态显示「未检测」，检测分区只显示「尚未检测。」。
- **理由：** 链接健康分区当初「打开页面不碰目标库」的理由仍然成立——目标库可能在断开的网络盘上，检测最长要等 45 秒超时；把它变成页面打开的常驻开销，等于每次进设置页都冒一次卡顿与报错。全手动也让「状态是什么时候的」只有一个答案。

| 选项 | 用户体验 | 技术正确性 | 风险 | 成本 |
|---|---|---|---|---|
| A 全手动（**决策**） | mixed | good | good | good |
| B 全自动（打开页面 / 换目标 / 共享后都重跑） | good | good | mixed | mixed |
| C 手动 + 事件触发（换目标 / 共享后自动重跑） | good | good | good | mixed |

- **被否决：** B 把最常见的入口变成一次目标库 IO，失败时用户还没做任何事就看到错误；C 会在共享完成后立刻访问目标库，把「检测」拆成一半手动一半自动，状态可能在用户没点检测时悄悄变化，与「检测是手动入口」的承诺不一致。
- **一致性说明：** 决策 A 的最弱轴是 ux（mixed）：首次进入全是「未检测」，用户必须先点一次才看得到任何状态。这是有意的：宁可让用户点一下，也不让页面打开就等目标库。

### D2 检测分区只留汇总，逐项状态与动作回到各分区（视觉反馈推翻原 Q2=D 的方向，Q2 重开待答）

- **决策：** 「目标库检测」分区只显示：徽标（只数链接的失效 / 不可达）、「检测」按钮、状态行、手动检测提示、链接汇总行、设置文件汇总行。**不列任何逐项行、不放任何批量按钮。** 逐项状态与处理动作回到资源自己的分区：插件 / 主题 / CSS 片段的行内显示目标状态 chip，链接失效的行带「重建链接 / 删除链接」，源库不可达的行只提示「先挂载源库（…）再检测。」；每个分区工具栏下方带「全部重建 / 全部删除」（只在该分区检测后有可操作项时出现）。设置的行保留状态 chip 与悬停差异详情，并新增行内「共享此项」。
- **理由：** 检测分区回答「目标库现在怎么样」，处理动作发生在问题所属的资源分区：用户在插件列表里看到某一行是链接失效，就在这一行重建；不需要先去上面的检测区找到同一个名字再回来核对。
- **来源：** 这条来自视觉反馈原文「目标库检测只显示检测结果汇总，具体每项检测情况放在下面每个分区的各项中，操作按钮也是放在每个分区，提供全部操作和单独项操作」。它推翻了 Q2 原先的 D（检测区列差异 / 缺失的文件），Q2 已被重开，但**尚未重新作答**；实现按本决策的方向执行（原型 v2 也按此画，未定部分标 `assumed`）。

| 选项 | 用户体验 | 技术正确性 | 风险 | 成本 |
|---|---|---|---|---|
| A 汇总-only + 逐项状态与动作回各分区（**方向**） | good | good | good | mixed |
| B 汇总 + 链接异常清单留在检测区 | mixed | good | good | good |
| C 汇总 + 全部异常清单与动作都在检测区（现状加强版） | mixed | good | mixed | good |

- **被否决：** B 让链接动作仍在检测区，与「在分区里处理」的边界不一致；C 是现状（检测区背所有动作），正是这次要改掉的。
- **一致性说明：** 决策 A 的最弱轴是 cost（mixed）：插件 / 主题 / 片段 / 设置四个分区的行渲染与工具栏都要改，还要各自加批量动作与行内动作；换来的是检测分区极简、动作就在问题旁边。

### D3 检测失败保留上次结果并标时间戳（q3 → A）

- **决策：** 任一段失败或超时，保留该段上一次成功的结果，在状态行写「链接检测失败：…（以下为 14:32 的结果）」或「设置文件检测失败：…（以下为 14:32 的结果）」，成功的那段另写「…已更新到 14:35」；从未成功过则只显示错误。逐段记录时间（链接段与设置段各自有上次成功时间，见 D5）。
- **理由：** 一次网络抖动不该把整页清空；用户刚看到的「3 个失效链接」比一片空白有用，时间戳足以说明它过期。

| 选项 | 用户体验 | 技术正确性 | 风险 | 成本 |
|---|---|---|---|---|
| A 保留上次结果 + 时间戳（**决策**） | good | mixed | mixed | good |
| B 失败即清空全部结果 | mixed | good | good | good |
| C 按来源两套规则（链接保留、设置清空） | mixed | mixed | mixed | mixed |

- **被否决：** B 让一次 45 秒超时把全部信息清掉，用户连「上次哪几份文件有差异」都失去参照；C 是现状的两套规则，正是这次要消掉的。
- **一致性说明：** 决策 A 的最弱轴是 risk（mixed）：用户可能对着上次的结果按「重建 / 删除」。这两类动作在插件里都会重新校验当前状态（链接已经健康会跳过、已不是链接会提示），真正不可逆的删除本身还有二次确认，因此过期状态的伤害有限。

### D4 共享完成后按影响面失效（q5 → C）

- **决策：** 设置共享完成 → 只清设置文件状态（链接结果保留）；插件 / 主题 / 片段共享完成 → 只清链接结果（设置状态保留）；换目标路径 → 两者一起清。都不自动重跑检测。
- **理由：** 失效范围应等于真正被改动的范围——设置共享没碰链接，资源共享没碰设置文件。

| 选项 | 用户体验 | 技术正确性 | 风险 | 成本 |
|---|---|---|---|---|
| A 任何共享后全部清空 | mixed | good | good | good |
| B 全部保留 + 整体标「过期」 | good | mixed | mixed | good |
| C 按影响面失效（**决策**） | good | good | good | mixed |

- **被否决：** A 会无谓清空未受影响的一半结果，并让用户重新承担整段扫描时间；B 的按钮仍可点，用户可能按过期结果重建链接或判断差异。
- **一致性说明：** 决策 C 的最弱轴是 cost（mixed）：现在 `invalidateTargetInventory`（`main.js:2865`）会顺手把设置状态一起清掉，要拆成两套失效逻辑，在两类共享完成处分别调用。

### D5 链接段与设置段各自超时、各自报错（q10 → A）

- **决策：** 一次「检测」并行执行两段：扫链接（`scanTargetVault`）与比较设置文件（`detectTargetSettings`），每段各自包 45 秒超时、各自的 token 丢弃保护与各自的完成时间；某段失败或超时不影响另一段的结果更新。状态行写明哪一段失败、哪一段更新到几点。
- **理由：** 两段耗时差一个量级——链接扫描在断开的网络盘上能吃掉全部 45 秒，设置比较只是读 8 个小 JSON。共用一个失败条件会让便宜的信息被前一段拖死。

| 选项 | 用户体验 | 技术正确性 | 风险 | 成本 |
|---|---|---|---|---|
| A 两段各自超时 / 报错（**决策**） | good | good | good | mixed |
| B 整次一个总超时 | mixed | good | good | good |
| C 先链接后设置，链接失败即中止 | mixed | mixed | good | good |

- **被否决：** B 让两段互相拖累；C 把没有依赖关系的两段人为串成依赖。
- **一致性说明：** 决策 A 的最弱轴是 cost（mixed）：两段各要一层超时、token 与错误状态，状态行也要区分是哪一段坏了。

### D6 改名：文案 + 代码标识符，历史 markdown 文档不回改（q8 → B）

- **决策：** 中文分区名「目标库检测」，英文「Target vault check」；「检测链接」按钮改成「检测」（英文 Check）；代码标识符与 CSS 类名整体从 `health*` / `plugin-share-linker-health-*` 改成 `targetCheck*` / `plugin-share-linker-target-check-*`（方法、TEXT key、类名一起改）。历史设计文档（`20261101_*`、`20261104_share-linker-vault-settings-design.md`）不回改，只在新文档里说明差异。
- **理由：** 分区不再只回答链接健康，内部继续叫 `health*` 会让概念与代码分叉，下次改这个分区还要先翻译；历史文档是当时决策的记录，回改会让它看起来从没叫过旧名。这条是命名型（Your call）问题，没有评分表，选的是偏好而不是效用。
- **被否决：** A 只改用户可见文案，代码里继续 `health*`；C 连历史设计文档一起替换。

## 常规选择

- **目标路径校验保持独立（q6 → A）：** 「检查目标路径」仍是目标路径行的独立按钮，结果卡仍渲染在页面底部；「检测」只做链接 + 设置，不先做路径校验。理由：路径能不能用与库里东西是什么状态是两件事，按钮就在检测分区正上方，发现成本低。
- **徽标只数链接问题（q7 → A）：** 徽标沿用「X 个失效 · Y 个不可达」/「未发现失效链接」，设置文件差异不进徽标，只出现在汇总行「设置文件：相同 5、有差异 2、缺失 1」与设置行 chip 上。理由：设置差异是「还没共享」，不是故障；混进徽标会让警示信号天天亮着。
- **设置分区保留行内状态（q4 → 见 Q2）：** 设置的行保留状态 chip（相同 / 有差异 N 个键 / 缺失 / 源库无此文件 / 源文件无法读取）与悬停差异详情；分区顶部保留原有的共享说明长句（合并规则、备份、排除项），句末指向上方「目标库检测」并提示「检测后在这里勾选要共享的文件，把鼠标移到文件行上可看差异详情」——只保留这一段说明，不再有检测状态行、检测按钮与自动检测。
- **检测区不列设置文件、不带逐项动作（q9 → A，随 D2 一起生效）：** 检测分区只留汇总，设置文件的逐项状态与共享动作都在设置分区。
- **旧原型最小修改（q11 → B）：** `docs/20261104_share-linker-vault-settings-visual.html` 只改自动检测的状态行文案与分区标题（改为指向「目标库检测」），保留文件行、勾选、确认弹窗、结果区这些仍然有效的交互，不整份重画。

**实现形态（本次改动清单）：**

- **分区结构：** 设置页分区顺序保持「目标路径 → 目标工具 → 目标库检测 → Obsidian 设置 → 插件 → 主题 → CSS 片段 → 结果区」。检测分区 = 头部（徽标 + 「检测」按钮 + 状态行）+ 提示行 + 两行汇总；不再有分组列表与批量按钮。
- **检测机制：** 原 `checkTargetLinks` 更名 `runTargetCheck`：同一轮里**并行**执行 `scanTargetVault` 与 `detectTargetSettings`（一段的耗时不会拖住另一段），各自 `runWithTimeout(…, 45000, actionTimeout(45))`、各自 token（期间目标路径被改则丢弃该段结果）、各自记录 `targetScanAt` / `settingsCheckAt`；成功后分别写 `targetInventory` / `settingStatuses`，**每段一落地就渲染自己那部分**（设置段不必等 45 秒的链接段），跑完再统一收尾。按钮在运行期间禁用，状态行显示「正在检测…」。状态行文案：成功「检测完成：3 个失效、1 个源库不可达；设置文件 4 份相同、2 份有差异、1 份缺失。」；某段失败时写「链接/设置文件检测失败：…（以下为 14:32 的结果）」并另写「链接已更新到 14:35」，失败段保留上次结果。链接段整体耗时记录在 `targetInventory.elapsedMs`，追加在链接汇总行后。
- **资源分区的行内动作：** 插件 / 主题 / CSS 片段的行，右列沿用 `renderTargetCell` 的 chip；链接失效行加「重建链接 / 删除链接」，源库不可达行只显示挂载源库提示；动作分别复用现有 `rebuildSingle` / `deleteSingle`（含确认与启用记录清理）。工具栏加「全部重建 / 全部删除」，分别作用于本分区内「当前库有同名资源」与「当前库没有同名资源」的失效链接，复用现有批量确认弹窗。
- **设置的行内动作：** 每行在 chip 旁加「共享此项」。实现按 Q12 的推荐 A（未正式作答）：打开只含这一份文件的确认弹窗（键名清单、`vaultBoundKeys` 警示、核心插件汇总都与批量共享一致），确认后走同一个 `applySettingsPlan`；勾选 + 「共享设置」的批量路径不变。
- **失效与刷新：** 把 `invalidateTargetInventory` 拆成 `invalidateLinkResults()` 与 `invalidateSettingsResults()`；统一检测只在手动按钮触发；删除 `settingsDetectTimer` / `scheduleSettingsDetect` / `refreshSettingsStatuses` 及其在 `refreshAll`（`main.js:2003`）、`checkTargetPath`（`main.js:2029`）、设置共享完成（`main.js:1807`）、换目标路径（`main.js:2882`）里的调用；设置共享完成后调用 `invalidateSettingsResults()`，资源共享完成后调用 `invalidateLinkResults()`，都不重跑检测。

## 风险

- **汇总-only 失去逐项清单一览：** 检测分区不再列异常，若用户不逐个滚动分区，可能漏看某一类问题。缓解：徽标数字 + 各分区工具栏的批量按钮只在异常出现时显示；要点是「异常多到需要总览」时，用户还能从四个分区的工具栏看到有异常的分区。
- **手动检测的首屏空白：** 首次进入全部显示「未检测」，用户可能没点检测就以为目标库没问题。缓解：检测分区的提示行明确「点检测才会访问目标库」，设置分区顶部保留指路提示。
- **保留旧结果可能被当作当前：** 失败时状态行与逐段时间戳是唯一区分。重建 / 删除动作会重新校验当前状态、删除有二次确认；但设置共享不看检测结果，仍可能按过期印象操作。
- **部分失败时两段状态时间不同：** 链接段过期而设置段新鲜（或相反），用户可能把两段的数字当成同一时刻。缓解：旧结果标「旧结果」，状态行写清哪段更新到几点。
- **全量改名遗漏：** `health*` 出现在 TEXT、方法名、CSS 类与测试里，漏改会同时出现新旧两套命名；历史文档与代码 / 新文档不一致（D6 有意）。
- **设置行「共享此项」：** 若实现复用了勾选状态，可能出现「勾了 A 却共享了 B」；实现必须独立构造只含该文件的 plan，确认弹窗只列这一份文件的键名。
- **网络盘上的检测仍可能 45 秒：** 手动检测下这是一次显式操作，可以接受；但用户连续点检测时按钮的禁用与状态行必须可靠。
